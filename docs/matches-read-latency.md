# 对局接口第二轮延迟优化

目标：`GET /api/public/matches?season=s2`。分支 `perf/matches-read-latency`。

2026-11-06，从当前代理环境连续只读请求 5 次，CF Ray 位于 LAX：

| 样本 | TTFB ms | 完整响应 ms | 服务端 ms | 生命周期检查 ms | 比赛 DB 等待 ms | 比赛 SQL ms |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 1167 | 1415 | 135 | 58 | 77 | 3.27 |
| 2 | 427 | 630 | 95 | 40 | 55 | 4.42 |
| 3 | 433 | 632 | 101 | 43 | 58 | 3.05 |
| 4 | 443 | 636 | 120 | 40 | 80 | 3.87 |
| 5 | 562 | 811 | 186 | 63 | 123 | 4.29 |

返回 128 场。SQL 计算不是主要耗时；仍存在两次串行数据库往返。以上不是国内三网测速，也不能据此保证用户侧响应时间。

实现：提取原有日切换检测 prepared statement，与比赛 SELECT 放入同一 D1 batch，普通读取仅一次往返。检测到边界到期后丢弃初次比赛快照，完成原有带租约的生命周期处理，再读取比赛。未缓存比分、未改变投票写入或调度频率、未新增索引、未迁移数据。原有 overview/votes 调度检查保持不变。

计时：普通请求的检查与比赛读取都计入 db_wait/db_queries；lifecycle 仅在实际推进时计时。不能把调整后的 lifecycle=0 理解为取消检查。

回归：先添加批量读取断言并确认失败，再实现；单元/集成测试验证一个 batch、历史字段不变、日切换响应已更新为当天 24 场 live。上线收益需要发布后在相同访问路径实测；预计减少一次数据库往返，不能把观察到的 40–63ms 直接当作收益保证。

验证结果：`npm run check`、143 项单元/集成测试、32 项浏览器测试、构建、七轮隔离赛季模拟均通过。改动留在独立开发分支，尚未合并或部署。

## 完整响应下载优化

线上补测：解压后 JSON 152,576 字节，已有 Brotli/gzip 自动压缩。单次 br 样本响应体读取约 206ms，gzip 253ms，identity 465ms；网络波动明显，不能当作严格编码性能对照，也不能把解压后字节数当作线上传输量。

新增对局接口 ETag 条件校验。每次仍先读主库并检查生命周期，计算最终响应的 SHA-256 弱 ETag；完全相同时返回无正文 304。`Cache-Control: private, no-cache` 允许浏览器保存但每次必须重新验证，不允许共享边缘缓存直接返回旧比分。投票、日切换、素材或名单变化都会影响完整响应校验值。初次请求、无浏览器缓存或数据变化时仍为完整 200；不承诺减少这类请求的网络往返时间。

该优化主要降低重复轮询的传输量，不降低数据库查询次数。没有把 128 场直接裁掉，因为赛程、历史比分、阵营统计和图鉴仍依赖完整对局数据；如后续拆分轻量比分接口，需要同步维护元数据更新与页面切换，另行验证。

条件请求验证：check、145 项单元/集成测试、构建与 32 项浏览器回归通过。专门测试确认 304 前仍执行读取、票数变化返回新的 200、错误不被 304 替代。尚未部署，尚未获得浏览器线上实际节省量。
