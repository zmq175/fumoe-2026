# 积分读取单次数据库往返

分支：`perf/standings-single-roundtrip`。本轮优化不涉及生产数据库迁移。

## 证据与选择

上一轮上线后实际请求中，`standings?season=s2` 的 Server-Timing 显示 `db_calls=2`、`db_queries=3`，总计约 138ms，而 SQL 约 3.95ms（代理链路样本，不能代表国内运营商体验）。因此优先减少一次数据库往返，而非新增没有证据支持的索引。

原流程先读取赛季及快照，再以赛季 ID 批量读取头像和实时积分。现在三个 SELECT 放在同一 D1 batch 内，以赛季 slug/当前赛季子查询关联，普通积分请求一次往返即可完成，并具有一致的批次读视图。

## 历史保护

- 锁定历史仍直接返回保存的 JSON，不重新生成或覆盖快照。
- 后两个查询对锁定快照返回零行，不计算该赛季比赛积分。
- 审计解锁后的计算规则、排序及头像规则保持不变。早期快照可能没有头像字段，直接返回时仍不补字段；实时计算保持原先的头像 null 行为。
- 当前赛季、显式 slug、草稿和不存在的赛季使用相同筛选语义；用户参数通过绑定传入。
- 投票写入、自动晋级、计分算法及定时频率未改变。

## 权衡

历史快照从一个 SELECT 变为一个包含三个 SELECT 的批次，后两个查询无数据；不会增加数据库网络往返，但有少量空查询开销。当前实时积分维持三个 SELECT，将两个网络往返减为一个。实际耗时和读行数收益需要发布后测量。

图片版本映射暂不拆成异步文件，避免关键图片等待映射、先下载原图后再下载压缩图，以及破坏历史素材绑定。

验证：check、148 项单元/集成测试、36 项浏览器测试、构建及七轮隔离赛季模拟全部通过。测试先复现两次往返，再验证单批次、历史快照内容不变、历史计算分支零行、解锁后字段与排序、草稿和不存在赛季的空结果。本轮未合并 main、未推送或部署。
