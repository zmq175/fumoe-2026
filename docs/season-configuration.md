# 可配置赛季

本次实现范围：2–256 人，分组瑞士轮接单败淘汰或直接单败淘汰；按赛季配置阵营；逐轮时长和轮前休赛间隔；草稿名单导入；发布校验和隔离模拟。循环赛、双败淘汰、团队赛、单轮分批开放尚不属于支持的赛制。

旧赛季 `rules_version=1` 且 `format_json=NULL` 始终使用原来的 128 人、8 组、3 轮瑞士轮及 16 强淘汰规则。新赛季存储完整的 v2 配置，未知版本拒绝执行。配置和名单仅草稿可修改，发布后冻结。

所有真实轮次独立保存开始和结束时间。配置中的休赛间隔发生在对应轮次之前。自动推进必须等到预定开始时间；延迟恢复整体平移剩余排期，保留原轮次时长及休赛间隔。

上线需要先导出生产备份，在隔离 D1 验证迁移及旧赛季赛果不变，再运行新迁移。代码开发和本地验证不会部署或迁移生产数据库。

## 后台操作

1. 创建草稿；可以选择复制已有名单，也可以空名单起步。复制不会修改来源赛季。
2. 设置人数、赛制、分组及晋级人数。人数目前须为 2 的幂，不支持轮空；分组可选 2、4、8、16 组。
3. 设置每轮时长、轮前休赛和本季阵营。阵营按游戏名称关联，游戏名称可新增，不依赖前端内置角色表。
4. 填写操作原因，保存配置；使用 TSV 导入名单，列为角色 ID、名称、游戏、组别、种子、简介。新 ID 创建角色，已有 ID 不允许冒用为其他姓名或游戏。
5. 执行完整赛季模拟。模拟读取已保存配置，按种子决定胜负，不写入真实对局和票数。
6. 检查人数、分组容量、种子唯一性并发布。未保存编辑会阻止发布；存在另一个当前进行中／已发布赛季时，服务端拒绝新发布。
7. 在逐轮日历中调整尚未开始的轮次，按需要启用自动推进或手动推进。暂停轮次需人工恢复。

月赛示例：256 人，16 组，每组 16 人，5 轮瑞士轮，每组晋级 2 人，再打 5 轮淘汰。共 10 轮，每轮比赛 48 小时、轮前休赛 24 小时，共 30 天（包含首轮前休赛）。

## 历史隔离与演进接口

- `season-format.ts` 集中解释并校验配置；配对、晋级、排期与公开签表共同消费该配置。
- `rules_version` 与 `format_json` 发布后被冻结。v2 指配置结构版本，本次仍沿用胜 3／平 1／负 0、积分／对手分／净票差／种子排序和淘汰赛种子破平规则，未开放任意积分表达式。
- 发布时保存角色和素材引用快照；完赛保存榜单快照。显式审计解锁、修正后重新锁定会更新榜单快照，这是受控历史修正，不是自动重算。
- 旧的静态肖像、立绘和阵营标志通过内容哈希归档；构建时校验原始文件，防止覆盖文件悄悄改变历史展示。新素材应使用新路径或媒体版本；缺失的版本不回退到其他版本图片。
- `0008` 保留旧参赛记录、放宽组别限制并增加配置冻结约束；`0009` 按原有榜单算法为既有已结束／归档赛季生成结果快照，不修改原始对局、票数、胜者。
- 下一种赛制需要增加有版本的配对／晋级实现、配置校验和对应视图，并通过新旧赛季隔离测试。当前不是任意赛制编排器，循环赛、双败、团队赛等仍需开发。

## 验证与上线边界

自动测试覆盖迁移前后旧记录一致性、256 人完整晋级与休赛间隔、名单和发布拦截、128 场批量投票以及桌面／手机配置入口。另有真实本地 Worker 的旧 128 人七轮演练。SQLite 集成测试并不替代生产 D1 演练。

本次发布前本地验证：`npm run check`、`npm test`（105 项）、`npm run test:e2e`（25 项）、`npm run build`、旧赛季完整七轮演练均通过。`wrangler deploy --dry-run` 仅构建检查，不代表已经上传或发布；生产迁移演练和部署结果须另行确认。

批量对局和投票采用集合 SQL，避免随人数增长堆叠参数和语句；约束依据 [Cloudflare D1 限制](https://developers.cloudflare.com/d1/platform/limits/)。

正式上线前须保留可恢复的生产导出，在隔离 D1 上执行迁移和完整演练，比对旧赛季票数、胜者与榜单；确认后再安排数据库迁移与应用部署。不要直接回退到不认识 v2 配置的旧 Worker 来承接已发布的新赛季。
